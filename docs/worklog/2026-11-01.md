## 2. Corner demo 구성과 첫 실주행

- **구성**: `corner_demo.launch.py`(control + LiDAR/EKF + slam_toolbox localization + perception + planning) → `run_corner.py`가 global localization(scan을 맵 전체에 맞춤, 약 6초) → `/initialpose` → slam_toolbox 수렴 확인 → planning에 목표 전달
- **global localization 실측**: 원점에서 먼 곳 3곳 모두 점수 0.94~1.00, slam_toolbox와 **4 cm 이내** 일치

| 증상 | 원인 | 수정 |
|---|---|---|
| 목표 1.4 m 앞에서 정지 | 시간 제한 60 s (0.12 m/s로 7 m 경로 초과) | control·planning timeout 180 s |
| 주행 중 갑자기 Fault | scan이 TF보다 몇 ms 앞서면 장애물 데이터를 지워 버림 | 변환 실패 시 직전 값 유지, Fault 메시지에 실제 원인 표시 |
| 같은 자리에서 계속 멈춤 | 경로가 벽에 padding(0.24 m) 그대로 붙어 지나가, 오차로 margin 안에 들어가면 재계획 영구 실패 | 경로를 벽에서 더 띄우고, margin 안이면 가까운 자유 칸으로 탈출 |
| Ctrl+C 했는데 계속 주행 | Ctrl+C가 메시지 수신 중에 걸리면 STOP을 건너뜀 | SIGINT를 flag로 처리, STOP 전송 확인 |
| 하드웨어 | USB hub 끊김으로 앞 LiDAR(`-110` timeout)·팔 보드 feedback 정지 | USB 리셋 / 보드 리셋 절차 정리 |

- **결과**: 실주행으로 **목표 구석 도착 확인**
- **RViz 도구**: 목표(`/corner/goal`), 계획 경로(`/corner/path`), 지나온 경로(`/corner/trail`), EKF 궤적 점(`/odometry/local/trail`, 사라지지 않음)

## 3. 오후: ㄷ자 벽 안쪽 출발 시 벽으로 돌진

- **원인 (오프라인 시뮬레이션으로 확인)**: control Pure Pursuit가 경로 전체에서 "차체 앞쪽의 첫 점"을 찾았다. 근처 경로가 뒤에 있으면(아래를 보고 출발) 몇 m 떨어진 경로 후반부를 집고 **제자리 회전 없이 직진**했다.
- **경로 계획 교체: A*+arc C++ 포팅**
  - 팀에서 만든 A*+arc(`astar_arc.py`: heading 상태 4방향 A*, 코너 원호 fillet, PASS/STOP_TURN/ALIGN)를 C++로 옮겨 기존 8방향 A*를 대체
  - Python과 **waypoint 40/40 일치**, 계획 시간 **중앙값 24 ms / 최대 49 ms**(Python 560 / 1058 ms)
  - 이름 정리: KANT → **A*+arc**
- **구간 분할**: 경로를 STOP_TURN 코너까지만 보내고, 도착하면 그 자리에서 다음 구간을 계획한다. 주행 중 주기적 재계획은 없애고 막혔을 때만 재계획한다.
- **control 추종**: "내 노드"를 직전 노드 ±3점 안에서 찾음(U턴 겹침 방지), lookahead는 경로를 따라 0.3 m, 방향이 0.5 rad 넘게 어긋나면 먼저 제자리 회전
- **테스트**: planning 76개, control 52개 통과 (새 시나리오: ㄷ자 출발, 완전히 겹치는 U턴)

## 4. 퍽 집기 설계 (구현 일부, 실측 대기)

- **잡기 가능 판정**: IK 대신 실험으로 구한 퍽 종류별(누움/섬) 영역. **정렬이 먼저**(누운 퍽은 장축이 차체 전방과 허용각 안), 정렬된 경우에만 퍽 중심이 영역 안인지 판정, 연속 3회면 확정
- **정지 위치 비용함수**: `J = w_box / (d − 3 cm) + w_grasp · ((s − s_good)/σ)²`
  - d: 로봇 앞면(LM 가이드)과 박스 사이 최단거리, 3 cm에서 무한대(안전거리)
  - s: 앞면에서 퍽 중심까지 거리, s_good: 잡기 좋은 면
  - 1/d형 장벽과 2차 장벽의 연산량 차이는 무의미(49 ns vs 7 ns)
- **하위 미션 설계**: 대기 지점 → 관측 → 정밀 접근 → 잡기 가능 정지 → 재확인 → 집기·적재
- **실측 대기**: 잡기 영역(모양과 값), 앞면 위치·폭, s_good. 퍽 centerpose(perception)는 TODO

## 6. 밤 ~ 11/2 새벽: LiDAR 각도 작업과 지면 처리

- LiDAR pitch를 올린 뒤 180° 화각에서 바닥이 찍혀 90°로 운용
- **평평한 바닥 보정** (높이 실측: 앞 1.2 cm, 뒤 1.1 cm)
  - 바닥 점이 V자 → 단순 평면(pitch + roll) 모델로는 설명 불가
  - 원뿔 0.6° + pitch 1.65°(바깥쪽 들림) + roll 0.1~0.2° 모델이 오차 **1 cm 수준**으로 맞음
  - 정면 바깥쪽 빔은 1 m당 1.8 cm 상승 → **7 cm 박스를 약 3.2 m까지** 볼 수 있음
- **경기장 데이터 기반 비대칭 ROI**: LiDAR별·좌우별로 바닥이 찍히기 시작하는 각도(바깥쪽 50~70°)까지는 전부, 그 바깥은 5° 구간별 최대 거리만 사용
  - 교차 검증: 보지 않은 bag에서 바닥 점 **75~90% 제거**, 맵 벽 점 80~97% 유지
  - `/lidar/merged`에 적용 → SLAM, 위치 찾기, 장애물이 모두 지면 없는 scan 사용, 화각 180°로 복귀
- RViz에 planner가 실제로 보는 장애물(필터 적용 후) 표시 추가
